Background

Theta, MinHash, and why LSH needs MinHash

Both sketches hash every item of a set and keep small hash values. Both estimate the Jaccard similarity J of two sets: the size of their overlap divided by the size of their union. They differ in which values they keep, and in where they keep them.

Why we are interested in MinHash

The problem. Find all similar pairs in a collection of N sets. A compare of every pair costs N(N − 1)/2 compares. LSH avoids this: it stores each set in b buckets, and it compares only the sets that share a bucket.

LSH needs aligned slots. In MinHash, slot i of A and slot i of B are the minimum of the same hash function. They are equal with probability J, and the k slots are independent. So a band of r slots is equal with probability Jr, and a pair becomes a candidate with probability 1 − (1 − Jr)b. Section 2d shows that the measured rate matches this. PR #18

Theta has no aligned positions. The position of a value in the sorted list depends on how many smaller values the set has. One extra small item moves every later value by one place. In a research experiment, bands cut from the sorted theta values collided at only 2 % to 17 % of Jr. Research A ADR-0003

LSH checks many candidate pairs. The MinHash jaccard() is a slot-by-slot count, about 240 to 360 times faster than the theta one (smoke run, section 2c). PR #15

Example. On 20 Newsgroups, LSH (b = 64, r = 4) took 0.30 s against 5.90 s for a MinHash compare of all pairs, with the same recall of 0.945. Research B

For one pair that a user chooses, theta is as good as MinHash or better (section 2b). MinHash is for finding the similar pairs in a large collection. ADR-0003

How LSH avoids comparing every pair

To find the near neighbours among N sets, a compare of all pairs calls jaccard() N(N − 1)/2 times. LSH calls it only for the sets that share a bucket. Section 2d gives the cost.

The index keeps one hash table for each band. A bucket is one entry of that table: a band key, and the sets that have that key in that band. The example below builds an index for four sets, with k = 8 slots cut into b = 4 bands of r = 2 slots.

Step 2: build the lookup tables. Here a "table" is a lookup table, like a dictionary: each row is a band key and a list of set ids. The index has one such table for each band, so 4 tables here. In the code each table is a std::unordered_map from the 64-bit band key to a list of ids. minhash_lsh.hpp

To add a set, add() computes its 4 band keys. For each band, it looks up the key in that band's table. If the key is not there, it adds a row with an empty list. Then it appends the set's id to the list. It compares nothing. minhash_lsh_impl.hpp

Step 3: read the tables to choose which pairs to compare. get_duplicate_clusters() reads every row of every table. A row with 1 id gives nothing to compare. The other use: look up one new set. query_candidates() answers "which stored sets could be similar to this one?". It computes the 4 band keys of the new set and looks up each key in its table. Take a new set E with the signature 17 05 | 91 18 | 33 21 | 66 72. Its band 1 key hash(17, 05) finds A, and its band 3 key hash(33, 21) finds A and C. Its other keys find nothing. So the candidates of E are A and C, and the caller checks only those two with jaccard(). minhash_lsh_impl.hpp

Result. The index made 4 × 4 = 16 list appends and 3 jaccard() calls. All pairs would make 6 calls. It never compared A and D, B and C, or B and D. Their estimates are 0, 0.13 and 0, so nothing above t was missed. The verified pairs give the clusters {A, B} and {C, D}, as get_duplicate_clusters() returns them. minhash_lsh.hpp

With 4 sets the saving is small. Section 2d shows how the saving grows with the number of sets.

What the index stores, and how it could be saved

The index does not replace the sketches. It adds memory on top of them. It has two parts. minhash_lsh.hpp

  • A copy of each sketch. add() copies the sketch into a map from id to sketch. Step 3 needs the slots, because jaccard() compares them. If your program also keeps its sketches, each signature is in memory twice. minhash_lsh_impl.hpp
  • The b lookup tables. There is one table for each band, not one for each slot. At k = 128 and b = 32, there are 32 tables, and each table covers r = 4 slots. Each set adds its id to exactly one row in each table, so the tables hold b ids for each set. A new band key also adds a row. In the example, the 4 tables hold 16 ids in 11 rows.

Saving the index. To serialise is to write a sketch or an index as bytes, so that a program can store it and read it back later. Today no code serialises the index, and no issue covers it. MH-23 covers the sketch, and it is deferred. MH-27 covers the planned Bloom-filter index, not this one. MH-23 MH-27

A draft sketch format is in fork commit d5ae896, on a branch that is not merged. The left table shows it. The right table is an example only, to show one way to save the index. Nobody has agreed it. d5ae896 ADR-0003

What the saved form holds. Each set has one record: its id and its k slot values. The record has no band keys, and the saved form has no tables. Each record has only an id and the slots, not a full sketch buffer, because all the sets in an index have the same k and seed (add() checks this).

How the tables come back. Each band key is an XXH64 hash of the r slot values of its band. So on load, the reader calls add() for each record, and add() makes the b tables again, with b hashes for each set. minhash_lsh.hpp

If the tables were saved too. The format would add the b tables after the records. Each table is a list of rows. Each row is one band key (8 bytes) and the ids of the sets that have that key (8 bytes each). Each set is in exactly one row of each table, so the tables hold n × b ids and at most n × b keys. That adds up to b × 16 bytes for each set, which is 512 bytes at b = 32.

Both forms keep the slot values. jaccard() compares slots, and the band keys alone cannot give an estimate of J. Judgement: without the tables, the saved form stays near the size of the signatures, 1,032 bytes for each set at k = 128, and the tables cannot disagree with the slots. With the tables, the load does not hash again, and a reader can find the rows of a key without reading every record.

How to query a saved index.

  1. Make an empty index with the b and t from the header. Then call add() for each record. The tables are now in memory again.
  2. Make the sketch of the new set with the same k and seed. query_candidates() rejects a sketch with a different k or seed.
  3. Call query_candidates(). It computes the b band keys of the new set, looks up each key in its table, and returns the sorted ids that share at least one key. It calls no jaccard().
  4. Check each candidate with jaccard(). The index has no public function that returns a stored sketch, so the caller uses its own copy of each sketch. This is one reason why a program can keep each signature twice.

To find all the similar pairs instead, call get_duplicate_clusters() after step 1. It does the jaccard() checks itself. minhash_lsh.hpp

1. The short answer

  1. MinHash is not more accurate than theta for each byte. At large set sizes, both sketches keep about k values of 8 bytes each, so their sizes are close. At equal bytes, they have about the same error. PR #17
  2. MinHash has no exact mode for small sets. A theta sketch of a small set stores all items, so it is exact and smaller. MinHash always uses 8k bytes and keeps its full error. PR #17
  3. The MinHash update costs O(k) for each item. It is 7 to 56 times slower than theta for k = 16 to 256. Two smoke-run tables give different ratios. PR #15 ADR-0003
  4. The MinHash estimate is correct. Its spread is within 3 % of the theory, it shows no bias for k ≤ 1024, and its bounds are safe. PR #16
  5. The aligned slots of MinHash make LSH possible. Theta has no aligned slots, so it cannot give band keys directly. ADR-0003
  6. The MinHash jaccard() is about 240 to 360 times faster than the theta one (smoke run). LSH verification makes many of these compares. PR #15
  7. The LSH S-curve agrees with the theory 1 − (1 − Jr)b at k = 64, 128 and 256 and at every power-of-2 number of bands. PR #18

Words used in this report

Jaccard similarity J
The size of the overlap of two sets divided by the size of their union. 0 means no shared item, 1 means the same set.
Set size n
Here, the number of items in the union of the two sets.
Slot, slot value, k
A MinHash sketch has k slots. Each slot keeps the smallest hash value that it received. The k slot values together are the signature.
Theta sketch, lg_k
The DataSketches sketch that keeps the smallest hash values of one hash function. It keeps between K and 15K/8 of them, where K = 2lg_k.
Exact mode, estimation mode
Theta is in exact mode while it keeps every item, and its answer is then exact. After that, it samples, and it estimates.
SD, bias
The standard deviation is the usual size of the error. The bias is the mean error.
Trial
One repeat of an experiment with a different random seed.
Bounds, coverage, nominal
jaccard_bounds() gives an interval for J. Coverage is the fraction of trials where the interval contains the true J. The nominal coverage is the target: 68.27 %, 95.45 % and 99.73 % at 1, 2 and 3 SD.
Band, r, b, band key
LSH cuts a signature into b bands of r consecutive slots. Each band gives one band key, a hash of its r slot values.
Candidate pair
Two sets that have the same band key in at least one band.
S-curve
The probability that a pair becomes a candidate, drawn against J. It has the shape of an S.
Serialise, format
To write a sketch or an index as bytes, so that a program can store it and read it back. The format is the layout of those bytes.
Full run, smoke run
A full run uses the complete grid. A smoke run is a short, small run that checks that the code works.

What was measured. For k = 16, 64, 256, 1024 and 4096, and for 99 values of J from 0.01 to 0.99, the profile made 4096 trials. Each trial compared two sets with a known J and a union of 10,000 items, and recorded the estimate, the error and the bounds. accuracy_j_findings.md accuracy_j.tsv

The theory says that the estimate has no bias and an SD of √(J(1 − J)/k). The profile checks both, and checks the bounds.

Key numbers

  • Spread. The measured SD is 0.9710 to 1.0246 times the theory SD over all 495 points. The expected noise is 1 ± 0.033. PR #16
  • Where 0.033 comes from. The SD at each point is measured from N = 4096 trials, so it has a random error of its own. The relative standard error of a measured SD is about 1/√(2N) = 1/√8192 ≈ 0.011. Three of these give 0.033. So even a perfect sketch gives SD ratios that move between about 0.967 and 1.033. accuracy_j_findings.md
  • Size of the error. At J = 0.5 the SD is 0.125 at k = 16 and 0.0078 at k = 4096. Each step from k to 4k halves it. accuracy_j_findings.md
  • Bias. For k ≤ 1024, the largest bias is 2.6 standard errors, so the run shows no bias. At k = 4096, the largest is 4.08 standard errors (J = 0.02), and all 99 points have a negative mean error. In absolute terms it is −1.4 × 10⁻⁴, against an SD of 2.2 × 10⁻³. PR #16
  • Bounds. No point is more than 3 standard errors below nominal. The lowest 2 SD coverage is 94.97 %, against 95.45 %. accuracy_j_findings.md
  • Bounds at small k. The bounds are wider than necessary. The mean 2 SD coverage is 98.3 % at k = 16 and 97.2 % at k = 64. At k = 4096 it is 95.7 %. accuracy_j_findings.md
  • Real data. The 20 Newsgroups demo passes its bias, spread and coverage checks at k = 64, 128, 256 and 512. minhash_20news.md

What this means

The estimate behaves as the theory says. A user can compute the error from k and J before building anything: SD = √(J(1 − J)/k). To halve the error, multiply k by 4.

The bounds from jaccard_bounds() are safe at every k and J in this profile. At k ≤ 64 they are wider than necessary, so the true uncertainty is smaller than they say.

The k = 4096 bias is not explained yet. It is reported on CD-395 for a decision. Judgement: it is about 6 % of one SD, so it is too small to change a result in normal use.

Why the lines are at these levels (k = 256, J = 0.5)

  • MinHash, at about 0.031. The theory SD is √(J(1 − J)/k) = √(0.25/256) = 0.5/16 = 0.03125. MinHash always keeps exactly k slot values, so its SD does not change with n. The measured line stays at 0.031 over the whole n range. accuracy_n.tsv
  • Theta, the same formula with r in place of k. Theta estimates J from the hashes that it keeps, so it has r samples instead of k. PR #17 Its SD is therefore about √(J(1 − J)/r). In the TSV files, this formula with the midpoint of r is 0.86 to 1.65 times the measured theta SD at n > 2048. At k = 256 and J = 0.5 it is 0.90 to 1.16 times, and at n > 16k it is 0.86 to 1.13 times. The largest values are just after theta leaves exact mode, for example 1.65 at k = 1024 and n = 3,444. There the formula overstates the theta SD. There r is a large part of n. Theta samples without replacement, which multiplies its variance by (1 − r/n), and this formula has no such term. PR #17 reports that the data fits √((k/r)(1 − r/n)) to within about 0.01 at k = 1024. PR #17
  • Why theta goes up and down. In estimation mode, r increases from K to 15K/8 as n increases. Then theta rebuilds its table, and r drops back to K. PR #17 So the theta SD decreases while r increases, and it jumps up at each rebuild. Each tooth covers an increase in n of about 1.875 times.
  • Theta at the same k (K = 256). r is between 256 and 480, so the SD is between √(0.25/256) = 0.031 and √(0.25/480) = 0.023. With r at about 1.4k, the SD is about 0.026.
  • Theta at half k (K = 128). r is between 128 and 240, so the SD is between √(0.25/128) = 0.044 and √(0.25/240) = 0.032. With r at about 0.7k, the SD is about 0.037.
  • Theta at 0. While theta keeps every item, it is in exact mode, so its error is 0. Here that is up to n = 470 at the same k and n = 235 at half k. accuracy_n.tsv accuracy_n_half.tsv

The values in this list are simple arithmetic on the formula and on the r range above. The comparison with the measured theta SD uses TH_RetainedA_Min, TH_RetainedA_Max and TH_MeasuredSD from the two TSV files.

Key numbers

  • Accuracy for each byte. At n = 65,536 and J = 0.5, the theta SD scaled by √(theta bytes / MinHash bytes) is 0.96 to 1.06 times the MinHash SD, at every k ≥ 64 in both profiles. Both sketches spend about 8 bytes for each sample. PR #17

What this means

For Jaccard estimation alone, MinHash gives no accuracy advantage. At large n and equal bytes, the two sketches are about equal. At small n, theta is better, because it is exact and smaller. Theta also gives cardinality, intersection and A-not-B, and MinHash does not. Research A

Large sets. Neither sketch is smaller for the same accuracy. Theta at the same k uses about 1.4 times the MinHash bytes, and it has a smaller error to match. Theta at half k uses about 0.7 times the MinHash bytes, and its SD is 1.13 to 1.21 times the MinHash theory SD. PR #17

Small sets. MinHash pays its full size and its full error at every n. This region needs its own investigation. The table above shows where it ends: about 1.7k to 1.8k items against theta at half k.

The plan for small sets. ADR-0003 defers an exact mode to a separate later issue. That mode keeps the seeded 64-bit XXH64 hash of each distinct item, so it uses 8 bytes for each item, as theta does in exact mode. It computes the k slot values from that list when it needs them. Thus the slot values and the test vectors do not change, and J is exact when both sketches hold a hash list. MH-23 will reserve one flag bit in format version 1 for this form. ADR-0003 does not set the n at which a sketch changes from the list to slots. ADR-0003

Judgement: a simple change point is n = k, where the list reaches the 8k bytes of the slots.

Judgement: a user who only estimates J of pairs that they choose should use theta. ADR-0003 states the same.

Key numbers

  • Update. MinHash costs about 0.47 ns for each slot and each item, so its update is O(k). The theta update is about O(1). PR #15 ADR-0003
  • Update ratio. From the PR #15 table, MinHash is 7.4, 20 and 20 times slower than theta at k = 16, 64 and 256 (simple division of the u64 column).
  • jaccard() ratio. From the same table, MinHash is 345, 237 and 363 times faster at k = 16, 64 and 256. The MinHash compare is a slot-by-slot count. Theta builds a union and an intersection for each call. PR #15 Research A
  • Build time on real data. In the all-pairs benchmark, theta built its sketches 5 to 9 times faster: 0.14 s against 0.76 s on 20 Newsgroups, and 0.59 s against 5.24 s on trajectory content. Research B

Why the speeds differ

The two sketches do their work at different times. MinHash does k units of work for each item when it builds, so that a compare is cheap. Theta does little work for each item, and it pays when it compares. The notes below come from the library code.

What each operation does
MinHashTheta
update()One XXH64 hash, then a loop over all k slots: one SplitMix64 step, one compare and one store for each slot.   • The MinHash update grows with k. 11.33, 35.32 and 122.8 ns at k = 16, 64 and 256: about 0.47 ns for each slot. PR #15
  • The theta update hardly depends on K, because the compare with θ rejects most items before any work that depends on K. It is 1.5 to 1.8 ns at k = 16 and 64. The 6.2 ns at k = 256 is one of the two values that the sources do not agree on (see below).
  • The hash is a small part of the MinHash update. From u64 to 64-byte strings, the theta update increases by about 5.6 ns at k = 16. The MinHash update at k = 256 increases by about 11 ns, which is less than 10 % of its 122.8 ns. Most of the MinHash time is the k slot steps. PR #15 (simple subtraction)
  • The MinHash jaccard() is a short loop. 22.95 ns for 256 slots is about 0.09 ns for each slot. The theta jaccard() takes 8321 ns at k = 256, because it allocates two hash tables, inserts into them and computes bounds. The profile keeps only the estimate, but the theta call computes the bounds too. PR #15 speed.cpp

Judgement: MinHash suits work with many compares, such as LSH verification. Theta suits work that builds many sketches and compares few of them.

Two sources disagree. Theta update at k = 256 (u64) is 6.2 ns per item in the PR #15 table, and 2.2 ns per item in the research document. So the update ratio at k = 256 is about 20 times (PR #15) or 56 times (research document, and ADR-0003 "8 to 56 times"). The jaccard() times also differ a little: 8,321 ns against 8,409 ns for theta, and 22.95 ns against 23.0 ns for MinHash. Both are smoke runs on a machine that was not quiet. PR #15 Research A ADR-0003

The merge times do not compare the same operation. MinHash merges in place into a copy. Theta builds a new theta_union and calls get_result(). The construct time of theta depends on an escape barrier that stops the compiler from removing the allocation. PR #15

What this means

MinHash is slow to build and fast to compare. Theta is fast to build and slow to compare. The update gap grows with k. The compare gap is about 240 to 360 times at every k tested.

ADR-0003 states that its decision rests on differences of 8 to 360 times, so the noise of the smoke run cannot change it. The exact ratios need MH-21.

The slow update is a choice. Format version 1 keeps the k-hash update of ADR-0002, so that correctness comes first. ADR-0003

The plan after correctness. The owner plans to investigate one-permutation hashing (OPH). OPH computes one hash for each item, not k hashes, so it can make the update about k times faster. ADR-0003 rejected densified OPH for version 1. Its band rate is 1.8 to 7 times too high for sets smaller than about 4 times the signature length. A different slot algorithm also changes the slot values and the test vectors, so it needs a new format version. ADR-0003

Judgement: the exact mode for small sets could remove the case where densified OPH fails. An OPH investigation must measure the band rate again, with the MH-19 profile.

What was measured. For k = 64, 128 and 256, and every power-of-2 b (with r = k/b), the profile measured the fraction of pairs that become candidates, at J = 0 to 1 in steps of 0.01, with 4096 trials. It compared that rate with the theory 1 − (1 − Jr)b. It also measured the reported rate: the fraction of pairs that are candidates and have an estimated J ≥ t, at thresholds t = 0.5, 0.7 and 0.9. PR #18

The profile uses band_keys() and the rule "equal in at least one band" directly, with no index. A unit test checks that the index finds exactly the same candidates. PR #18

Key numbers

  • Agreement. Over the 585 rows where a z-score is valid, the largest |z| is 3.20. Over the 1,440 rows with small counts, the smallest exact two-sided p-value is 0.0066. With 400 to 550 such rows for each k, a value near 0.002 is normal. No row has a measured rate that differs where the theory is exactly 0 or 1. PR #18 lsh_accuracy.md
  • Example. At k = 128, b = 32, r = 4: the measured candidate rate is 0.046 at J = 0.2 (theory 0.050), and 0.873 at J = 0.5 (theory 0.873). At J = 0.8 every pair is a candidate (theory 0.99999995). lsh_accuracy.tsv
  • Small sets. A separate MH-6 test measures the band rate J4 within ±15 % at k = 128, r = 4, a union of 10 items and J = 0.2, over 800,000 band observations. ADR-0003
  • Theta cannot do this directly. In a research experiment, bands cut from the sorted theta hashes collided at only 2 % to 17 % of Jr. A one-hash scheme (densified OPH, 256 bins) collided 1.8 to 7.25 times too often for sets smaller than about 4 times the signature length. Research A ADR-0003

How to choose bands and rows

The table gives, for k = 128, three values for each choice of (b, r) and each threshold t. J50 is the J where the reported rate first reaches 0.5. "False positive" is the reported rate at J = t − 0.1. "Miss" is 1 − the reported rate at J = t + 0.1. At t = 0.9 the miss rate is always 0, because t + 0.1 = 1. lsh_accuracy.md

Recommended action: add sizing helpers

Other sketches in the library have static helpers that size a sketch before a user builds it. Examples: count_min_sketch::suggest_num_buckets() and suggest_num_hashes(), bloom_filter::builder::suggest_num_filter_bits() and suggest_num_hashes(), kll_sketch::get_normalized_rank_error() and hll_sketch::get_rel_err(). MinHash and LSH have no such helpers.

Judgement: add them, because MH-16 and MH-19 show that the formulas match the measured results. Possible helpers:

  • The candidate probability 1 − (1 − Jr)b for a given J, b and r.
  • A suggested b for a given k and threshold t: the smallest b that divides k and puts the S-curve midpoint close to t.
  • The SD √(J(1 − J)/k) for a given k and J, and the k for a target SD.

Filed as MH-30 (CD-410), a placeholder in the Production readiness backlog.

What LSH costs

A compare of all pairs makes N(N − 1)/2 jaccard() calls. LSH makes N · b hash-table inserts, then one jaccard() call for each candidate pair.

The number of operations (simple arithmetic on the two formulas)
Sets NBands bAll pairs: jaccard() callsLSH: inserts
1,00032499,50032,000
100,00032about 5.0 × 10⁹3.2 × 10⁶

Why the candidate list is short. A pair becomes a candidate with probability 1 − (1 − Jr)b. This is nearly 0 for a small J and nearly 1 for a large J. At k = 128, b = 32, r = 4, the measured rate is 0 at J = 0, 0.046 at J = 0.2, 0.873 at J = 0.5 and 1 at J = 0.8. lsh_accuracy.tsv In a real collection, almost all pairs are dissimilar. On 20 Newsgroups, 1,993,324 of 1,999,533 pairs have J = 0. minhash_20news.md So the cost is about N · b inserts, plus the near neighbours, plus a few chance candidates.

Limits. LSH removes the quadratic cost only when most pairs are dissimilar. If most sets are similar to each other, most pairs become candidates again. If most pairs have J ≈ 0.2, about 4.6 % of all pairs become candidates: still quadratic, but with a smaller constant. One large bucket of many different sets that share a band key is quadratic inside that bucket. MH-13 (CD-335, #22) removed the case of identical signatures: get_duplicate_clusters() now groups them and links them with no jaccard() call. minhash_lsh_impl.hpp MH-20 will measure the LSH cost against all pairs.

What this means

The index finds candidates at the rate that the theory predicts. A user can therefore choose b and r on paper, from the formula, and trust the result.

The table shows two effects. First, if the S-curve rises well above t (few bands of many slots), the index misses most pairs near t. Second, when J50 is near t, more bands still lower the miss rate, and they raise the false-positive rate a little. At k = 128, b = 64 instead of 32 lowers the miss rate from 0.0198 to 0.0090, and the false-positive rate goes from 0.0144 to 0.0146. At k = 64, b = 32 instead of 16 lowers the miss rate from 0.1282 to 0.0352, and it raises the false-positive rate from 0.0518 to 0.0691. lsh_accuracy.md The remaining errors come from the MinHash estimate. A larger k reduces them: compare k = 64, 128 and 256 at r = 4 above.

Judgement: b is a trade-off. Fewer bands give fewer band keys and fewer candidates to check, but more misses near t. Choose b from the miss rate and the false-positive rate that the use can accept, from the table above. MH-20 will measure the cost of more bands.

4. Still open

  • MH-20: LSH against brute force. Not done. This is the LSH performance profile. The only numbers so far come from the research benchmark: on 20 Newsgroups, LSH (b = 64, r = 4) took 0.30 s against 5.90 s for MinHash all-pairs, with the same recall of 0.945. Research B
  • MH-21 (CD-401): full timed runs. Not done. They need a quiet machine. The estimate is about 1.2 h for the update profile and about 30 s for the call profile. PR #15 README
  • MH-24 (CD-404): exact mode for small sets. Deferred by ADR-0003. Until it exists, the small-set gap of section 2b is a known limit. An exact mode would not change any slot value or test vector. ADR-0003
  • MH-23: serialization. Not done. Format version 1 must reserve one flag bit for a later hash-list form, and a version 1 reader must reject a buffer with that bit or any unassigned bit set. ADR-0003
  • MH-31 (CD-411): one-permutation hashing. Backlog placeholder. Planned after correctness is established, to make the update about k times faster. It needs a new format version and a new band-rate check (section 2c).
  • MH-30 (CD-410): sizing helpers. Backlog placeholder. Recommended in section 2d.
  • Open decisions from the results. The k = 4096 bias (CD-395). Whether k = 512 or 1024 closes the recall gap to theta (0.945 against 0.999 on 20 Newsgroups). The trajectory data has no pair with J ≥ 0.5 among 62M pairs, so a near-duplicate demo on it would find nothing. PR #16 Research B
